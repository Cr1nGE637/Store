2 ПРОЕКТИРОВАНИЕ

На основе требований, сформулированных в аналитическом разделе, необходимо выполнить проектирование веб-приложения для онлайн-продажи электроники. В рамках проектирования необходимо определить следующие аспекты программного продукта:

- общую структуру системы;
- назначение серверной и клиентской частей;
- архитектурный подход;
- модульную структуру приложения;
- доменную модель;
- взаимодействие модулей;
- структуру хранения данных;
- основные пользовательские сценарии.

2.1 Общая структура проектируемой системы

Проектируемая система представляет собой веб-приложение интернет-магазина электроники. Она должна обеспечивать просмотр каталога, работу с карточкой товара, добавление товаров в корзину, оформление заказа, учет складских остатков, проверку совместимости товаров и административное управление данными магазина.

На верхнем уровне систему целесообразно представить в виде трех основных частей: клиентская часть, серверная часть и хранилище данных. Клиентская часть должна обеспечивать взаимодействие пользователя с приложением. Серверная часть должна принимать действия пользователя, проверять доступ, выполнять бизнес-правила и обращаться к хранилищу данных. Хранилище данных должно сохранять состояние системы: сведения о пользователях, товарах, категориях, характеристиках, корзинах, заказах, остатках, резервах, уведомлениях и правилах совместимости.

2.1.1 Назначение серверной и клиентской частей

Клиентская часть предназначена для отображения информации и приема действий пользователя. Покупатель через нее просматривает каталог, открывает карточки товаров, применяет фильтры, работает с корзиной, оформляет заказ и просматривает свои заказы. Менеджер использует административный интерфейс для управления товарами, категориями, изображениями, характеристиками, складскими остатками и правилами совместимости.

Серверная часть отвечает за обработку действий пользователя и выполнение правил предметной области. Все операции, изменяющие состояние системы, должны выполняться на серверной стороне. К таким операциям относятся создание товара, изменение характеристик, оформление заказа, резервирование товара, изменение состояния заказа и проверка совместимости выбранных позиций.

Клиентская часть может выполнять предварительные проверки, связанные с удобством работы пользователя, например проверку заполнения формы. Окончательное решение о допустимости операции должна принимать серверная часть, поскольку именно она контролирует права доступа и корректность изменения данных.

2.1.2 Основные проектируемые компоненты

В общей структуре проектируемой системы выделяются следующие компоненты: пользовательский интерфейс покупателя, административный интерфейс менеджера, серверная часть, механизм проверки доступа, механизм обработки бизнес-сценариев, механизм внутреннего взаимодействия процессов и хранилище данных.

Пользовательский интерфейс покупателя предназначен для выполнения сценариев выбора и покупки товаров. Административный интерфейс менеджера предназначен для сопровождения данных магазина. Серверная часть должна координировать выполнение операций, проверять права пользователя и применять бизнес-правила. Механизм внутреннего взаимодействия процессов нужен для связи действий, которые относятся к разным частям системы, например оформления корзины, создания заказа, резервирования товаров и формирования уведомления.

2.2 Выбор архитектурного подхода

Выбор архитектурного подхода определяет способ организации серверной части, распределение ответственности между компонентами и правила их взаимодействия. Для интернет-магазина электроники архитектура особенно важна, поскольку система включает несколько связанных процессов: каталог, корзину, заказы, складской учет, пользователей, уведомления и проверку совместимости.

Для выбора архитектурного подхода были рассмотрены монолитная, микросервисная и модульная архитектуры.

2.2.1 Сравнение монолитной, микросервисной и модульной архитектуры

Монолитная архитектура предполагает разработку приложения как единой системы. Такой подход прост в запуске и развертывании, однако при отсутствии внутренних границ логика разных процессов может смешиваться. Например, оформление заказа может напрямую затрагивать корзину, складские остатки и уведомления.

Микросервисная архитектура предполагает разделение системы на отдельные сервисы, каждый из которых отвечает за собственную область. Такой подход дает высокую независимость компонентов, однако требует сложной инфраструктуры: сетевого взаимодействия, мониторинга, согласования данных и надежной доставки сообщений.

Модульная архитектура занимает промежуточное положение. Система развертывается как единое приложение, но внутри разделяется на самостоятельные модули. Это позволяет сохранить простоту единого приложения и задать границы между частями предметной области.

Таблица 2.1 - Сравнение архитектурных подходов

| Критерий | Монолитная архитектура | Микросервисная архитектура | Модульная архитектура |
|---|---|---|---|
| Разработка первого прототипа | Наиболее простая | Сложная из-за нескольких сервисов | Близка к монолиту |
| Развертывание | Одно приложение | Несколько сервисов | Одно приложение |
| Инфраструктурная сложность | Низкая | Высокая | Умеренная |
| Изменение связанных сценариев | Есть риск затронуть общий слой логики | Требует согласования сервисов | Локализуется в модулях и контрактах |
| Тестирование бизнес-правил | Зависит от внутреннего разделения | Возможно по сервисам, сложнее интеграционно | Возможно по отдельным модулям |
| Риск избыточной сложности | Низкий на старте | Высокий для текущего масштаба | Средний |

2.2.2 Обоснование выбора модульной архитектуры

На основе сравнения было принято решение использовать модульную архитектуру. Такой выбор связан с тем, что интернет-магазин электроники включает несколько процессов, которые участвуют в одном сценарии покупки, однако обладают разными правилами. Каталог отвечает за товарные данные, корзина - за временный выбор пользователя, заказы - за фиксацию покупки, склад - за доступность и резервирование, проверка совместимости - за анализ характеристик.

Обычный монолит обеспечивает простой запуск, однако без дополнительных границ повышает риск смешивания логики. Микросервисная архитектура обеспечивает физическое разделение частей системы, но для текущего масштаба приводит к избыточной инфраструктурной сложности. Модульная архитектура позволяет сохранить единое приложение и одновременно разделить бизнес-логику по предметным областям.

Таким образом, на этапе проектирования модульная архитектура принята как компромиссный вариант между простотой монолита и разделением ответственности, характерным для микросервисов.

2.5 Проектирование взаимодействия модулей

После выделения модулей необходимо определить способ их взаимодействия. Для проектируемого интернет-магазина это важно, поскольку один пользовательский сценарий может затрагивать несколько областей системы.

При проектировании взаимодействия модулей были определены следующие условия: модуль не должен изменять внутренние данные другого модуля напрямую; обмен данными должен выполняться через явно определенные контракты; значимые изменения состояния должны передаваться через события; повторная обработка события не должна приводить к дублированию операций.

2.5.1 Контрактное взаимодействие между модулями

Контрактное взаимодействие предполагает, что модуль предоставляет внешней части системы ограниченный набор данных, не раскрывая внутреннюю реализацию. Контракт должен содержать только те сведения, которые необходимы получателю.

2.5.2 Событийное взаимодействие при оформлении заказа

Событийное взаимодействие используется для передачи информации о значимых изменениях состояния. Наиболее важным сценарием является оформление заказа, поскольку оно затрагивает корзину, заказы, складской учет и уведомления.

Проектируемая последовательность включает следующие шаги: покупатель оформляет корзину; модуль корзины фиксирует оформление; формируется событие; модуль заказов создает заказ; модуль складского учета резервирует товары; при успешном резервировании заказ переходит в состояние ожидания оплаты; при ошибке резервирования пользователь получает возможность изменить корзину.

2.5.3 Использование механизмов Outbox и Inbox

Событийное взаимодействие требует надежной обработки событий. Если событие возникло, однако осталось необработанным из-за сбоя, система может перейти в некорректное состояние. Например, корзина была оформлена, а заказ не создан либо товар не зарезервирован.

Механизм Outbox предусматривается для сохранения событий, которые должны быть обработаны после изменения состояния модуля. Событие должно сохраняться вместе с основными изменениями данных, после чего обработчик получает необработанные события и передает их получателям.

Механизм Inbox предусматривается для контроля уже обработанных событий. Он должен защищать систему от повторной обработки. Это особенно важно для заказов, складского учета и уведомлений: повторное создание заказа, повторное резервирование товара или повторная отправка уведомления должны быть исключены.

2.6.3 Хранение характеристик товаров, остатков и резервов

Для интернет-магазина электроники особое значение имеют характеристики товаров, складские остатки и резервы. Характеристики должны храниться в структурированном виде, поскольку разные категории электроники имеют разные параметры. Например, для процессора важен сокет, для оперативной памяти - тип памяти, для накопителя - интерфейс и емкость.

Для хранения характеристик целесообразно предусмотреть структуру, в которой характеристика связана с товаром и содержит название параметра, значение и единицу измерения. Такая структура позволит отображать характеристики в карточке товара, использовать их в фильтрах и передавать в механизм проверки совместимости.

Складские остатки должны храниться отдельно от товарной карточки. Товар в каталоге описывает то, что продается, а складская позиция описывает, сколько единиц товара доступно для продажи. Для складского учета необходимо различать общее количество товара и доступное количество, которое учитывает созданные резервы.

Резерв хранит связь между заказом и количеством товара, временно закрепленным за этим заказом. При оплате заказа резерв списывается со склада, при отмене заказа резерв освобождается.
