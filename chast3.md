3.1 Требования к реализации

В результате реализации были разработаны основные компоненты веб-приложения, предусмотренные на этапе проектирования: клиентская часть, серверная часть, модули каталога, корзины, заказов, складского учета, пользователей, уведомлений и проверки совместимости товаров. Также была реализована административная часть для управления товарами, складскими остатками и правилами совместимости.

Поскольку разрабатываемая система включает большое количество типовых операций, в данном разделе подробно рассматриваются не все элементы приложения, а наиболее сложные механизмы, определяющие архитектурную и предметную ценность проекта. К ним относятся:

- модульная организация серверной части;
- изоляция бизнес-логики внутри доменных моделей;
- оформление заказа через взаимодействие корзины, заказа и склада;
- резервирование и списание складских остатков;
- событийное взаимодействие между модулями;
- механизмы Outbox и Inbox;
- проверка совместимости товаров на основе правил;
- выбранный технологический стек реализации;
- реализация основных пользовательских сценариев.

3.1.1 Выбранные технологии реализации

Для реализации серверной части был выбран стек на основе C#, .NET 9 и ASP.NET Core. Данный выбор связан с тем, что ASP.NET Core предоставляет готовую инфраструктуру для разработки HTTP API, внедрения зависимостей, настройки middleware, аутентификации, авторизации, фоновых служб и интеграции с документацией API. Это позволило реализовать серверную часть как единое веб-приложение, внутри которого отдельные предметные модули регистрируются независимо и сохраняют собственные границы ответственности.

Для доступа к данным используется Entity Framework Core с провайдером Npgsql.EntityFrameworkCore.PostgreSQL. В качестве системы управления базами данных выбрана PostgreSQL. Такой вариант подходит для модульного приложения, поскольку каждый модуль может иметь собственный DbContext и отдельную схему базы данных. Это поддерживает архитектурную изоляцию модулей и одновременно сохраняет преимущества единого реляционного хранилища. Миграции EF Core применяются для управления структурой таблиц, а транзакционная модель PostgreSQL используется при сохранении агрегатов, outbox-сообщений и служебных записей inbox.

Для организации application-слоя применяется MediatR. Команды, запросы и обработчики позволяют отделить HTTP-контроллеры от сценариев использования. Контроллеры принимают запросы клиентской части и передают их в соответствующие обработчики, а основная логика выполнения сценариев остается в application-слое и доменных моделях. Для представления результата операций используется CSharpFunctionalExtensions, что позволяет явно возвращать успешный результат или ошибку без смешивания бизнес-проверок с исключениями.

Безопасность реализована с использованием JWT-аутентификации и ролевой модели. Пароли пользователей хешируются с помощью BCrypt.Net-Next. Для отправки email-уведомлений используется MailKit, а для импорта и экспорта товарных данных в формате Excel - ClosedXML. Документирование и проверка серверного API выполняются через Swagger / Swashbuckle.

Клиентская часть реализована на React 19 с использованием TypeScript и Vite. React выбран для построения интерактивного пользовательского интерфейса каталога, корзины, оформления заказа, списка заказов и административной панели. TypeScript повышает надежность работы с моделями данных API, а Vite ускоряет разработку и сборку frontend-приложения. Для маршрутизации используется React Router, для загрузки и кеширования серверных данных - TanStack React Query, для стилизации компонентов - styled-components.

Развертывание приложения выполняется с использованием Docker и Docker Compose. В инфраструктуре выделены контейнеры серверной части, клиентской части и PostgreSQL. Клиентская часть при контейнерном запуске обслуживается через Nginx. Такой подход упрощает запуск системы, поскольку все основные зависимости приложения описаны в едином compose-файле.

Для проверки корректности реализации используется xUnit. Тесты охватывают доменные модели, application-сценарии, инфраструктурные элементы и архитектурные ограничения. Наличие тестов особенно важно для данного проекта, так как основная ценность системы связана не только с пользовательским интерфейсом, но и с корректностью бизнес-правил, событийного взаимодействия и изоляции модулей.

3.2 Реализация модульной структуры серверной части

Серверная часть приложения реализована как модульное приложение. Внешне она предоставляет единый программный интерфейс для клиентской части, а внутри разделяется на предметные модули. Такое устройство соответствует проектной модели, в которой каталог, корзина, заказы, склад, пользователи, уведомления и проверка совместимости выделены в самостоятельные области ответственности.

В решении выделены следующие серверные модули:

- Store.Identity;
- Store.Catalog;
- Store.Carts;
- Store.Ordering;
- Store.Inventory;
- Store.Notifications;
- Store.Consulting;
- Store.EventOutbox;
- Store.SharedKernel.

Модуль Store.Identity отвечает за пользователей, регистрацию, вход и роли. Модуль Store.Catalog реализует каталог товаров, категории, изображения и характеристики электроники. Store.Carts отвечает за корзину покупателя и запуск оформления заказа. Store.Ordering реализует создание и сопровождение заказов. Store.Inventory отвечает за складские остатки, резервы и списание товаров. Store.Notifications формирует уведомления. Store.Consulting реализует проверку совместимости товаров. Store.EventOutbox содержит общий механизм обработки доменных событий, а Store.SharedKernel хранит общие элементы доменной модели.

3.3 Реализация изолированной бизнес-логики внутри доменных моделей

Одной из основных задач реализации являлось отделение бизнес-логики от технических деталей. Поэтому правила изменения состояния размещены в доменных агрегатах. Контроллеры и обработчики команд не принимают ключевые бизнес-решения самостоятельно, а вызывают методы доменных объектов.

Примером является агрегат Cart. Он отвечает за состав корзины и контролирует, можно ли добавлять товар, изменять количество, удалять позицию или начинать оформление заказа. Если корзина уже находится в состоянии ожидания оформления, изменение состава запрещается. Это защищает систему от ситуации, при которой пользователь меняет корзину во время создания заказа.

Фрагмент реализации метода оформления корзины представлен ниже.

```csharp
public Result<IReadOnlyList<CartItem>> Checkout(
    string customerEmail,
    string recipientName,
    string phone,
    string deliveryAddress,
    string deliveryMethod,
    string paymentMethod,
    DateTimeOffset? checkoutStartedAt = null)
{
    if (IsCheckoutPending)
        return Result.Failure<IReadOnlyList<CartItem>>("Cart checkout is pending");

    if (_items.Count == 0)
        return Result.Failure<IReadOnlyList<CartItem>>("Cart is empty");

    if (string.IsNullOrWhiteSpace(customerEmail))
        return Result.Failure<IReadOnlyList<CartItem>>("Customer email is required");

    var snapshot = _items.ToList();
    var checkoutEvent = new CartCheckedOutEvent(
        CartId,
        CustomerId,
        customerEmail.Trim(),
        checkoutDetails.RecipientName.Value,
        checkoutDetails.Phone.Value,
        checkoutDetails.DeliveryAddress.Value,
        checkoutDetails.DeliveryMethod.Value,
        checkoutDetails.PaymentMethod.Value,
        eventItems);

    IsCheckoutPending = true;
    PendingCheckoutId = checkoutEvent.EventId;
    CheckoutPendingSince = checkoutStartedAt ?? DateTimeOffset.UtcNow;
    RaiseDomainEvent(checkoutEvent);

    return Result.Success<IReadOnlyList<CartItem>>(snapshot);
}
```

В данном фрагменте видно, что оформление корзины выполняется через доменную модель. Метод проверяет состояние корзины, наличие товаров и данные покупателя. После этого создается снимок товаров, формируется событие CartCheckedOutEvent, а корзина переводится в состояние IsCheckoutPending. Такое состояние нужно для защиты корзины на время межмодульной обработки.

Аналогичный подход используется в агрегате Order. Заказ хранит статус и контролирует допустимые переходы между состояниями. Например, заказ нельзя оплатить, если он ожидает резервирования товара, отменен или отклонен. После успешного резервирования заказ переходит в статус Unpaid, после оплаты - в статус Paid, при ошибке склада - в статус Rejected.

3.4 Реализация сценария оформления заказа

Наиболее сложным сценарием серверной части является оформление заказа. Его сложность связана с тем, что одно действие пользователя затрагивает несколько модулей: корзину, заказы, складской учет, уведомления и каталог. При этом нельзя допустить потери корзины, повторного создания заказа или резервирования недоступного товара.

Сценарий начинается с запроса клиентской части к API корзины. Обработчик команды загружает корзину текущего покупателя и вызывает метод Checkout доменной модели. После успешной проверки корзина сохраняется, а доменное событие помещается в Outbox.

Фрагмент обработчика команды оформления представлен ниже.

```csharp
public async Task<Result<CheckoutResultDto>> Handle(
    CheckoutCommand request,
    CancellationToken cancellationToken)
{
    var cartResult = await cartRepository.GetByCustomerIdAsync(request.CustomerId);
    if (cartResult.IsFailure)
        return Result.Failure<CheckoutResultDto>(cartResult.Error);

    var cart = cartResult.Value;

    var checkoutResult = cart.Checkout(
        request.CustomerEmail,
        request.RecipientName,
        request.Phone,
        request.DeliveryAddress,
        request.DeliveryMethod,
        request.PaymentMethod);
    if (checkoutResult.IsFailure)
        return Result.Failure<CheckoutResultDto>(checkoutResult.Error);

    await cartRepository.UpdateAsync(cart);
    await outbox.AddAsync(cart.DomainEvents, cancellationToken);
    await unitOfWork.SaveChangesAsync(cancellationToken);
    cart.ClearDomainEvents();

    return Result.Success(CartMappings.ToCheckoutResultDto(cart, checkoutResult.Value));
}
```

Обработчик не создает заказ напрямую. Он фиксирует оформление корзины и сохраняет событие. Дальнейшая обработка выполняется другими модулями.

3.4.1 Создание заказа на основе корзины

После публикации события CartCheckedOutEvent его обрабатывает модуль заказов. Обработчик проверяет, было ли событие обработано ранее. Если заказ с таким идентификатором оформления уже существует, повторное создание не выполняется. Это защищает систему от дублирования заказа при повторной доставке события.

Далее позиции корзины преобразуются в товары заказа. После этого создается агрегат Order. Новый заказ получает статус AwaitingStock, поскольку перед оплатой необходимо проверить наличие товаров на складе и зарезервировать их.

Фрагмент обработчика события оформления корзины представлен ниже.

```csharp
public async Task Handle(
    CartCheckedOutEvent notification,
    CancellationToken cancellationToken)
{
    if (await inbox.HasProcessedAsync(notification.EventId, Consumer, cancellationToken))
        return;

    var existingOrderResult =
        await orderRepository.GetBySourceCheckoutIdAsync(notification.EventId);
    if (existingOrderResult.IsSuccess)
    {
        inbox.AddProcessed(notification, Consumer);
        await unitOfWork.SaveChangesAsync(cancellationToken);
        return;
    }

    var orderResult = Order.Create(
        notification.CustomerId,
        notification.CustomerEmail,
        notification.RecipientName,
        notification.Phone,
        notification.PaymentMethod,
        productResults.Select(r => r.Value).ToList(),
        notification.EventId);

    var order = orderResult.Value;
    await orderRepository.AddAsync(order);
    await outbox.AddAsync(order.DomainEvents, cancellationToken);
    inbox.AddProcessed(notification, Consumer);
    await unitOfWork.SaveChangesAsync(cancellationToken);
    order.ClearDomainEvents();
}
```

В результате обработки создается заказ и публикуется событие OrderStockReservationRequestedEvent. Оно сообщает складскому модулю, что по заказу необходимо выполнить резервирование товаров.

3.4.2 Резервирование товаров на складе

Модуль склада реализует учет общего и зарезервированного количества товара. Для этого в агрегате StockItem хранятся два значения: Quantity и Reserved. Доступное количество вычисляется как разница между ними.

```csharp
public int Quantity { get; private set; }
public int Reserved { get; private set; }
public int Available => Quantity - Reserved;
```

При резервировании склад проверяет наличие товара, создает резерв и увеличивает значение Reserved. Если доступного количества недостаточно, резервирование отклоняется.

```csharp
public Result Reserve(Guid orderId, int amount)
{
    if (orderId == Guid.Empty)
        return Result.Failure("OrderId is required");
    if (amount <= 0)
        return Result.Failure("Amount must be positive");
    if (_reservations.Any(r => r.OrderId == orderId))
        return Result.Failure($"Stock already reserved for order {orderId}");
    if (Available < amount)
        return Result.Failure($"Insufficient stock: available {Available}, requested {amount}");

    var reservationResult = StockReservation.Create(orderId, amount);
    if (reservationResult.IsFailure)
        return Result.Failure(reservationResult.Error);

    _reservations.Add(reservationResult.Value);
    Reserved += amount;
    RaiseStockChangedEvent();

    return Result.Success();
}
```

Обработчик события OrderStockReservationRequestedEvent сначала группирует товары заказа по идентификатору. Затем для каждой позиции загружает складскую запись и проверяет доступное количество. Если хотя бы по одной позиции резервирование невозможно, модуль публикует событие OrderStockReservationRejectedEvent. Если все позиции доступны, создаются резервы и публикуется событие OrderStockReservedEvent.

3.4.3 Изменение состояния заказа при результате резервирования

После обработки складом модуль заказов получает один из двух результатов. При успешном резервировании заказ переводится из статуса AwaitingStock в статус Unpaid. Это означает, что товары закреплены за заказом и пользователь может перейти к оплате. При отклонении резервирования заказ переводится в статус Rejected, а причина отказа сохраняется в заказе.

Такой сценарий позволяет не очищать корзину до успешного создания заказа и подтверждения склада. Если резервирование невозможно, пользователь может изменить состав корзины и повторить оформление.

После оплаты заказа модуль Ordering публикует событие OrderPaidEvent. Модуль Inventory обрабатывает его и списывает ранее зарезервированные товары. При отмене заказа публикуется OrderCancelledEvent, по которому резерв освобождается.

3.5 Реализация событийного взаимодействия модулей

Взаимодействие модулей реализовано через доменные события. Событие фиксирует факт, который уже произошел в одном модуле и может быть полезен другим модулям. Такой подход снижает прямую связанность между частями системы.

Например, корзина не обращается к модулю заказов напрямую. Она публикует событие CartCheckedOutEvent. Модуль заказов обрабатывает это событие и создает заказ. Заказ, в свою очередь, публикует событие запроса резервирования. Модуль склада обрабатывает его и сообщает результат. После изменения состояния заказа могут быть сформированы уведомления.

3.5.1 Публикация и обработка событий

Каждый агрегат может формировать доменные события во время изменения состояния. После сохранения агрегата события передаются в Outbox. Далее фоновый обработчик получает необработанные события и публикует их через механизм внутрипроцессной доставки.

Фрагмент фонового обработчика Outbox представлен ниже.

```csharp
var messages = await dbContext.Set<DomainEventOutboxMessage>()
    .Where(x => x.ProcessedOnUtc == null &&
                !x.IsDeadLettered &&
                (x.NextAttemptOnUtc == null || x.NextAttemptOnUtc <= now))
    .OrderBy(x => x.OccurredOnUtc)
    .Take(BatchSize)
    .ToListAsync(cancellationToken);

foreach (var message in messages)
{
    try
    {
        var domainEvent =
            DomainEventSerializer.Deserialize(message.EventType, message.Payload);
        await publisher.Publish(domainEvent, cancellationToken);
        message.MarkProcessed();
    }
    catch (Exception ex)
    {
        message.MarkFailed(ex.Message, MaxAttempts, BackoffBaseSeconds);
    }

    await dbContext.SaveChangesAsync(cancellationToken);
}
```

Обработчик выбирает события, которые еще не были обработаны, восстанавливает объект события из сохраненного представления и передает его подписчикам. При успешной обработке событие помечается как обработанное. При ошибке увеличивается количество попыток и назначается время следующей обработки.

3.5.2 Реализация механизмов Outbox и Inbox

Механизм Outbox используется для надежной публикации событий после изменения состояния модуля. Событие сохраняется в той же логической операции, что и изменение доменного объекта. Благодаря этому система не теряет событие, если после сохранения данных произойдет сбой.

Механизм Inbox используется для идемпотентной обработки входящих событий. Перед выполнением обработчик проверяет, был ли конкретный EventId уже обработан данным consumer. Если событие уже обработано, повторная операция не выполняется.

Такой подход особенно важен для заказа и склада. Повторная доставка события оформления корзины не должна создавать второй заказ. Повторная доставка события резервирования не должна увеличивать резерв дважды. Повторная доставка события оплаты не должна списывать товар повторно.

3.6 Реализация проверки совместимости товаров

Отличительной частью разработанного приложения является модуль Consulting. Он реализует проверку совместимости товаров на основе характеристик электроники. Такой механизм нужен для ситуаций, когда покупатель выбирает несколько связанных устройств или комплектующих.

Проверка совместимости выполняется не через жестко заданные условия в интерфейсе, а через правила, которыми может управлять менеджер. Правило содержит исходную категорию товара, целевую категорию, ключи сравниваемых характеристик, оператор сравнения, уровень проблемы и текст сообщения.

Примерами правил являются:

- сокет процессора должен совпадать с сокетом материнской платы;
- тип оперативной памяти должен поддерживаться материнской платой;
- интерфейс накопителя должен соответствовать поддерживаемому интерфейсу устройства;
- мощность блока питания должна быть больше или равна требуемому значению.

Схема проверки совместимости товаров представлена на рисунке 3.9.

[Рисунок 3.9 - Схема работы модуля проверки совместимости]

3.6.1 Структура правил совместимости

В модуле Consulting используются правила CompatibilityRule и условия CompatibilityCondition. Условие задает, какие характеристики нужно сравнить и какой оператор применить. В системе предусмотрены операторы Equals, NotEquals, In, GreaterThanOrEqual и LessThanOrEqual.

Результат проверки может иметь один из статусов: Ok, Warning, Error или Unknown. Статус Ok означает, что проблем не найдено. Warning используется для предупреждений. Error означает несовместимость. Unknown применяется в ситуации, когда у одного из товаров отсутствует характеристика, необходимая для проверки.

Таблица 3.2 - Операторы правил совместимости

| Оператор | Назначение | Пример применения |
|---|---|---|
| Equals | Проверка равенства значений | Сокет процессора совпадает с сокетом платы |
| NotEquals | Проверка различия значений | Исключение запрещенного сочетания |
| In | Проверка вхождения в список | Тип памяти входит в список поддерживаемых |
| GreaterThanOrEqual | Сравнение числового значения | Мощность блока питания достаточна |
| LessThanOrEqual | Проверка верхней границы значения | Потребление устройства не превышает лимит |

3.6.2 Алгоритм проверки выбранных товаров

Проверка выполняется доменным сервисом CompatibilityChecker. На вход он получает выбранные товары и активные правила. Для каждого правила выбираются товары исходной и целевой категорий. Затем сервис перебирает пары товаров и сравнивает значения характеристик.

Фрагмент реализации проверки представлен ниже.

```csharp
public ConsultationResult Check(
    IReadOnlyCollection<ConsultationProduct> products,
    IReadOnlyCollection<CompatibilityRule> rules)
{
    var issues = new List<CompatibilityIssue>();
    var recommendations = new List<ProductRecommendation>();

    foreach (var rule in rules.Where(r => r.IsActive))
    {
        var sourceProducts = products
            .Where(product => CategoryMatches(product, rule.SourceCategoryCode))
            .ToArray();

        var targetProducts = products
            .Where(product => CategoryMatches(product, rule.TargetCategoryCode))
            .ToArray();

        foreach (var sourceProduct in sourceProducts)
        foreach (var targetProduct in targetProducts)
        {
            if (sourceProduct.ProductId == targetProduct.ProductId)
                continue;

            var issue = CheckPair(rule, sourceProduct, targetProduct);
            if (issue is null)
                continue;

            issues.Add(issue);
        }
    }

    return new ConsultationResult(
        ResolveStatus(issues),
        issues,
        recommendations,
        DateTime.UtcNow);
}
```

Внутри метода CheckPair выполняется получение характеристик товаров. Если хотя бы одно значение отсутствует, создается проблема с уровнем Unknown. Если значения присутствуют, они сравниваются по оператору правила. Для числовых сравнений строковое значение предварительно приводится к числовому виду.

3.6.3 Формирование результата проверки

Результат проверки содержит общий статус, список найденных проблем и рекомендации. Общий статус определяется по наиболее серьезной проблеме. Если есть ошибка, результат получает статус Error. Если ошибок нет, но есть предупреждения, устанавливается Warning. Если отсутствуют необходимые характеристики, устанавливается Unknown. При отсутствии проблем возвращается Ok.
